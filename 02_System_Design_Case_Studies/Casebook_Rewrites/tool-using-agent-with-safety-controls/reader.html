Case brief

Understand the scenario, task, and constraints.

Let an agent prepare work without granting it authority

An operations team wants an agent to read customer email, query internal systems, update customer relationship management (CRM) records and sometimes issue refunds. Everyone agrees on that feature list and then disagrees about everything else. Operations wants speed. Security wants hard approval gates. The support manager wants routine cases handled without friction. Finance fears money that moves and cannot come back. That disagreement is the design problem.

The useful part of the agent is interpreting a messy request. The dangerous part is letting that interpretation become authority. A customer email is input to interpret, and it may also carry instructions written to manipulate the agent. Tool output is the same: a CRM row or a fetched page can contain hostile text. One injected sentence must never turn into a refund.

So the model proposes one bounded next action, meaning a single small step with stated limits, never "do everything". Deterministic services, which give the same answer for the same input and do not depend on the model's judgement, then take over. A validator checks the tool and its arguments. A policy service answers allow, block or needs a human. A credential broker issues a short-lived token that covers only that action. An idempotent gateway, a write path that turns repeated calls for the same action into one effect, runs it once and writes a receipt. Neither an email nor the model's confidence can authorise a refund.

The figure is the whole case in miniature. Every later section adds detail to one of its boxes, and none of them lets the planner skip a box. Writes fail closed, meaning that when a control cannot answer, the write does not happen. Operators can stop work already in flight by revoking tokens and cancelling queues.

Five groups of people meet in this system. The business user delegates inbox and case work. An approver reviews the exact risky payload. Security defines identity, authorisation and audit rules. Each tool and data owner defines supported operations, limits and the revert procedure. Operators monitor, reconcile uncertain actions and stop workflows. Step 1 maps what each of them notices first when the agent fails.

The first release excludes free-form code or shell execution, open-ended tool discovery, unbounded loops, cross-tenant access, self-modifying policy and unrestricted refunds. The case assumes you are comfortable with large language model (LLM) agents and tool calling, authentication and scoped tokens, idempotent APIs and basic cloud architecture.

This is the anchor case for agents that act. Several related prompts keep the same proposal-to-execution boundary and change which control dominates. The table shows where each one lands in this casebook.

Design walkthrough

Follow the reasoning from discovery to delivery.

1. Define an autonomy matrix for actions

Open with the disagreement rather than the feature list, and restate the ask as an outcome someone can test: enable useful automation while deterministic controls govern identity, permissions, risk and irreversible effects. A spoken version of that opening, from the source:

"We want an agent that reads email, checks internal systems, updates CRM, and sometimes issues refunds. The useful part is interpreting the request; the dangerous part is letting that interpretation become authority. I'll let the model propose actions, while identity, policy, approval, and an idempotent gateway decide what can actually happen."

Then ask the questions that change what may be built, not the ones that merely sound thorough. Ask which actions are reversible, where money and permission boundaries sit, and whether the agent acts as a user, a service account or a delegated actor. Record what may run, what needs review and what is forbidden. Autonomy differs by action class. A public FAQ lookup and a payment cannot share one enable switch.

The table lists the seven questions that change the controls. Each row pairs the formal question with the plain-language worry behind it and the decision the answer drives.

Does the agent act as the user, a service account, or a delegated actor? If a bad email tricks the agent, whose account takes the damage: the user's, a shared robot, or a narrow "this ticket only" role? How wide the token is, and how much one injected instruction can change.

How can operators stop an in-flight task? If a bad refund loop is already running, how do we stop work already started, not only the next chat? Kill switch must halt new tool calls, cancel queued work, and revoke tokens.
What workload and business outcome matter? How busy is peak, and are we optimising for faster handling or fewer wrong refunds? Planner/tool size, how many approvers you need, and how much autonomy you ship.

Is email untrusted? It is not on the list because the answer is always yes. A message may carry instructions to override policy, exfiltrate data or trigger a tool, and tool output carries the same risk, so the design assumes it rather than asking.

The answers decide more than thresholds. Reversibility and the money boundary decide whether you are building a control system with payment and escalation rules or an assistant with a few tools. The identity question sets blast radius, the amount of damage one mistake can reach: full-record access widens it, while access limited to the fields of one case contains what an injected instruction can change. Audit and retention are design inputs that shape the ledger schema, not something added after launch. The kill-switch question tells the interviewer you expect the system to be stoppable before it is perfect. Finally, whether success means fewer handling minutes, a higher resolution rate, a lower error rate or better satisfaction decides which metric the business inspects, and that metric sets how much autonomy is worth the risk.

With retention unspecified, store enough to reconstruct any action and leave the exact period to the customer's dispute and privacy policy. With tenancy unclear, assume strict isolation and a separate authorisation check at every tool boundary. Do not invent a permissive refund limit to complete the diagram.

The source grades answers in three tiers, and the difference between them is where authority sits. The weak answer connects the agent to email and CRM and lets it refund when it decides the customer deserves one. The model is the authority, it holds credentials rather than scoped capabilities, and nothing stops an instruction hidden in a ticket. The average answer plans tool calls, checks permissions before each one, requires approval for large refunds, logs everything and adds retries. It still trusts tool output, never bounds loops or spend, and retries without idempotency, which is how one refund quietly becomes two. The strong answer has the planner propose one bounded action, a typed schema validate it, a policy engine return allow, block or needs-approval, a broker mint a token for that single action and an idempotent gateway guarantee one effect. Tool observations are data, and loops, spend, refund amounts and destinations all have hard ceilings.

2. Make safety and performance testable

A requirement the customer cannot test is a preference. "It should be safe" is a preference. "No arbitrary command execution" is a constraint, and only the constraint changes the architecture. Separate three kinds of statement: what the system must do (functional), how safely and how well it must do it (non-functional), and what it must never do (non-goals).

Interviewers often ask for the six functional must-haves cold, and they work as a set:

  1. Separate planning from execution. The model proposes; a separate control layer decides whether any tool call may run.
  2. Validate tool name, arguments, identity and policy against an allowlist, a parameter schema, the caller's identity and the policy rules before anything runs.
  3. Use scoped, short-lived credentials. The agent never holds a broad secret and receives only the minimum for the next approved step.
  4. Require approval for high-risk actions. Refunds, account changes and any irreversible external write cross a human boundary unless the customer accepts a narrower automated threshold.
  5. Make effects idempotent and auditable, so a retry cannot double-refund and every decision leaves a replayable trace.
  6. Stop safely under uncertainty. Poor confidence, a malformed tool response, unclear policy or an inconsistent environment means pause, escalate or fail closed, never improvise.

Three should-haves complete the first usable version: a declared registry with schema and data class for every tool, so an undeclared tool cannot be called; a kill switch that halts autonomous paths without a deploy, tested before launch; and approval captured as a first-class record. The could-haves wait: richer policy expression, adaptive risk scoring, queued multi-step orchestration, replay tooling, operator dashboards, anomaly detection on action patterns and per-tenant policy overlays.

Declare the non-goals out loud, because strong candidates draw a narrower boundary than the prompt suggests: free-form code execution or shell access, open-ended tool discovery, unbounded autonomous loops, automatic refunds without approval thresholds, cross-tenant data access and self-modifying policy logic.

3. Draw the nine components and their boundaries

The LLM is the agent's planner, not its executor. It reads task state and tool results, proposes one bounded action, and can continue only after the policy, approval, gateway and receipt path completes. The whiteboard version of the architecture has seven steps:

  1. Establish delegation. Authenticate the user and determine which actions the user may delegate.
  2. Plan one bounded step. The planner reads task state and proposes one next action within its step and cost budgets.
  3. Validate the tool call. Resolve the tool's typed schema and check arguments, data class and action limits.
  4. Apply policy. Block and record a disallowed action, allow a safe one, or request human approval for the exact payload before it expires.
  5. Grant narrow authority. For an allowed or approved action, the broker issues a short-lived scoped token. Budgets and the kill switch still apply.
  6. Execute once through the gateway. The idempotent gateway calls the target system and prevents a retry from becoming a second side effect.
  7. Close the loop. Store the action receipt in the audit ledger and task state, and continue planning only from the recorded result.

Say each boundary as you draw it. The planner can propose. The registry defines legal tool shapes. Validation rejects malformed or over-limit arguments. Policy decides. Approval binds to the exact state. The broker supplies one narrow capability. The gateway is the only write path. A proposal is not proof of execution; the receipt is.

The full design reads the same system as nine components in dependency order, which is the order they have to exist and also the order they fail. The table gives each one's job, the trust boundary it guards and what happens when it is unavailable.

The organising split in the full diagram is control plane against data plane. The control plane decides what the agent is allowed to do, under what conditions and with which approvals. The data plane performs the bounded business work once those decisions are made. The model sits entirely inside the control plane's proposal step and never touches the data plane directly. The source draws the decision half and the execution half separately, then the two planes together.

Four trust-boundary sentences are worth saying verbatim. The user boundary ends at authentication. The planner boundary ends at proposing intent, not action. The policy boundary ends at allow, deny or approve. The execution boundary ends at a scoped, logged side effect in a downstream system of record.

Name the systems of record explicitly. The CRM owns customer attributes and a support view of refund history. The refund or payment service owns whether money actually moved; reconcile the CRM view against its transaction receipt. The email system owns transport and inbox state. The internal data source owns account and entitlement data. The task state store owns workflow progress but not business truth. Caches may sit beside the planner or registry for low-risk lookups, but they never become the source of truth for permissions or refunds. Tool outputs stay untrusted data wherever they are stored.

Not every boundary is synchronous. Planning the next action and evaluating policy are synchronous, because a person is waiting on a gating decision. Tool execution can be synchronous for one low-latency action, but bulk and slow steps go through queues. Audit writes can be asynchronous only while the log never falls behind the point where a failure becomes unrecoverable. When risk rises faster than capacity, apply backpressure: if approvers are saturated, slow autonomous execution instead of letting risky actions pile up. Partition work by workflow or account, so all actions for one account share a key and two conflicting refunds cannot run in parallel.

The ledger audits requests, proposals, policy verdicts, approvals and receipts. Monitoring watches denials, unsafe actions, duplicate effects, approval delay and overrides. The kill switch halts new calls, cancels queued work, revokes tokens and marks in-flight work, as step 6 explains.

4. Trace an email-to-refund task

Walk the representative request in order without skipping a handoff: "Read the customer's email, check whether the account qualifies for a refund, update the CRM note, and issue the refund if policy allows." The interviewer should hear where control moves from the model to deterministic services and back.

  1. Authenticate the delegating user. The front door verifies who is asking and what delegation rights they hold. A support agent is not a finance approver.
  2. Plan the bounded next action. The planner picks the next smallest step, such as "retrieve the latest email thread", never the whole workflow.
  3. Resolve the tool schema. The registry returns the exact contract, including field names and data-sensitivity labels.
  4. Validate arguments and data classification for shape, missing fields, dangerous content, the amount, account and destination, and regulated data that changes handling.
  5. Evaluate policy and risk. The policy point compares the action, user role, data class and downstream effect against current policy. A CRM note update may pass; a refund may need approval.
  6. Obtain approval if required, captured as a record bound to the exact payload, tenant, record version, amount and expiry.
  7. Execute with a scoped credential and an idempotency key, so a retry cannot duplicate the refund.
  8. Record the result and decide whether to continue. The ledger stores the input, policy result, approval outcome, tool result and side effects. The planner proposes another bounded step only if the new task state and evidence justify it; otherwise it stops.

The email text read in step 2 is an observation, so it enters task state as data with its provenance, never as an instruction. An approval records reviewer, timestamp, rationale, exact payload, tenant, record version, amount and expiry. The gateway revalidates that snapshot at execution time, so a changed amount or record version invalidates the old approval.

The data model follows from the walk, and two of its records must never be conflated: the proposal and the receipt. AgentTask(id, actor, goal, state, step_budget) records progress. ToolDefinition(name, schema, data_class, scopes) describes the legal operation. ActionProposal(id, task_id, tool, args_hash, policy_decision) is a recommendation. PolicyDecision(proposal_id, verdict, scopes, reason) is authority. ActionReceipt(proposal_id, idempotency_key, outcome) records execution. A proposal is not evidence that a side effect occurred.

Canonicalise arguments before hashing, meaning put them in one fixed form (field order, number format, whitespace) so the same logical input always yields the same idempotency seed. A repeated key returns the stored receipt when one exists. Persist the operation before dispatch, reject conflicting arguments for that identity, and distinguish prepared, in-flight, confirmed and uncertain states. If the downstream effect completed before the receipt was saved, reconcile through the same operation key rather than dispatching a new write. The source also ties every refund to a durable business-action identifier built from case, customer and policy decision. That matters because two legitimate refunds with identical arguments are two operations and need distinct identities; this example is our illustration of the source rule.

The gateway, not the planner, owns exactly-once effect semantics, and only within the idempotency contract the downstream system supports. A local cache of completed responses is not enough on its own. A lost response is an unknown outcome that needs reconciliation; neither a prompt nor a generic retry makes it safe.

Schema validation runs before policy evaluation, so malformed or over-limit arguments are rejected before any authorisation logic executes. If the policy point or broker cannot be reached, the write does not proceed.

5. Hold four security controls together

Start security from the hostile case. A message that looks like ordinary customer email is a prompt injection asking the agent to ignore policy, pull a privileged record and issue an unauthorised refund. Do not argue about whether the model understands the instruction. Contain the blast radius, preserve the evidence and keep every irreversible action behind deterministic checks. The model sees information; it does not inherit trust.

Four controls answer almost any "how do you secure an agent with tool access" question, so learn them as a set:

  1. Treat tool observations as untrusted. A CRM response, ticket thread, database row or fetched page can carry hostile instructions. If the model can read it, the model can be manipulated by it, so tool output is never a command, a policy override or an approval signal.
  2. Never give the model broad, long-lived credentials. A broker mints capability tokens tied to one tenant, one workflow, one action type and one expiry window. If the broker is down, writes fail closed.
  3. Validate output before downstream use. The model may propose "refund $5,000", and a $500 task limit rejects it however confident the model sounds. Validation is where policy becomes enforceable.
  4. Bound the dangerous dimensions with hard ceilings on tool calls, per-task spend, maximum refund amount, allowable CRM objects and destinations.

The $5,000 and $500 figures are the source's dollar example for validation. They are separate from the euro-denominated near miss in the deep dives. Typed arguments, required fields, enumerated action types and explicit data classes leave the model less room to invent an action. Restricted adapters expose supported operations without a shell escape.

Blast radius is a design variable along four axes: tenant, region, workflow and dependency. A single-tenant outage beats a cross-tenant incident. A regional backlog beats a global write failure. A failure in the refund workflow should not block email triage, and a broker outage should not take down read-only analytics that can safely degrade.

Defence in depth means no single control carries the load. Policy constrains the model, the action layer validates its output, the broker scopes identity, the gateway tracks idempotency, the ledger preserves evidence and the operator can kill the workflow. If an interviewer asks for the single most important control, name all six. A prompt telling the model to refuse unsafe requests can sit on top of them, but it enforces nothing.

6. Decide how each failure stops or recovers

Design the failure path together with the happy path. Five rules organise every row of the table below:

  1. Reads that support a recommendation may degrade or queue.
  2. Writes that change customer state fail closed when authorisation, validation or identity is uncertain.
  3. Irreversible effects require approval or a second deterministic check.
  4. A write is never retried without proven idempotency.
  5. Incomplete evidence means stop and escalate.

Only explicitly approved, non-sensitive read paths may degrade to cached evidence. An unavailable broker must never trigger use of a broad static secret to keep a demo alive.

The source says to read the policy-engine row slowly, because it is the row candidates most often soften. Now replay the path under the failure that matters most: a malicious instruction arrives inside an email.

Follow the figure from the top. The planner still extracts a bounded action from the email. The registry marks the email content as untrusted. The policy decision point rejects the illustrated attempt to expand scope. A subtler injection may request a formally allowed action on the wrong customer or for the wrong purpose. A successful tool call whose response was lost is an unknown outcome. Query its operation key or transaction record. The kill switch stops new tool calls, cancels queued work, requests token revocation and marks in-flight tasks for rejection where downstream services support it. A self-contained token may remain acceptable until expiry if the resource server does not check revocation state. Measure propagation delay and require the gateway to check a current cancellation or authorisation epoch before each write. A dashboard flag that only blocks new user requests is not enough. Even the full version has limits, which are our qualification rather than the source's: a completed external effect cannot be retracted by a flag, and a downstream API that ignores the in-flight mark needs reconciliation. Document those limits and the downstream revert path.

Before launch the team needs evidence and a runbook. The evidence shows which prompt version ran, which proposals were generated, which validations passed or failed, which approval artifact was attached, which identity token was used and which external calls were made. The runbook tells an operator how to quarantine a workflow, revoke a capability, replay a safe read-only step and reconcile uncertain writes without making things worse. A read-only replay can be safe; replaying a write needs its receipt and idempotency contract. Together they answer, after the fact, what happened, what was allowed, what was blocked and what the recovery path was.

7. Size the work behind each task

One request is not one unit of work. The source planning anchor is 50,000 users, twenty arriving tasks per second (QPS, queries per second) at peak and ten tool actions per task, which is about 200 tool actions per second. Separate three layers of load: how often tasks arrive; how many tool calls, model calls and policy checks each task triggers; and how many of those actions can change records, money or permissions. Iterative planning bursts can create forty to sixty model calls per second, so planner admission, model quota, adapters, approval queues and the ledger each need their own estimate.

Source planning estimates and their resulting bottlenecks.

Estimate Number What it forces
Planning decisions 20 per second at peak; 40 to 60 model calls per second under iterative planning bursts The planner is a queueing problem before it is a throughput problem; size planner and tool adapters separately
Tool actions roughly 200 per second at peak Reads parallelise; writes and approvals do not; concurrency caps must assume worst-case composition
Audit storage ~5 KB decision record and ~20 KB audit trail per task, so 100 KB/s to 400 KB/s About 8.6 GB to 34.6 GB per day of raw append-only data before indexing and replication

The estimate that most affects the design is not CPU. It is the ratio of model time to tool time, plus how irreversible the tool effects are. If planning is fast and tools are slow, invest in async orchestration, caching and queueing. If tool effects are high-risk, invest in policy checks, staged execution and audit logging, even at some cost in latency. If human review is the bottleneck, write clearer escalation rules and reduce the number of ambiguous cases that reach a person.

Derive the risk tier before deciding autonomy. The source's decision aid is Risk = Impact × Likelihood × Irreversibility, used as a qualitative aid, not literal arithmetic.

Place this case's actions in the four tiers. A low-impact read of a public FAQ can be fully autonomous. A CRM update is partly reversible, yet it still costs something if it misroutes a customer, so it runs with preconditions. A refund may be technically reversible and still meaningfully irreversible through customer dissatisfaction, accounting noise or abuse, so it needs human approval. Some exports and permission changes are blocked entirely.

Show a sensitivity range instead of false precision. The tenfold growth case is the real test: which part breaks first, the planner, the approval queue, a tool adapter, the audit log or the refund service?

Check the audit arithmetic rather than repeating the range. At twenty tasks per second, the 5 KB decision record alone is 100 KB/s, or about 8.6 GB/day, and the 20 KB audit trail alone is 400 KB/s, or about 34.6 GB/day. The source quotes these as a range. If every task writes both, the raw total is about 500 KB/s, or 43.2 GB/day, before indexing and replication. Plan storage on the larger figure unless the two records are known to overlap.

The source also budgets about one second of planner compute per task, or twenty core-seconds per second under a CPU-service interpretation. Remote model serving must instead be sized by request concurrency, token throughput and provider quota. A one-second API wait is not a one-core compute requirement.

At 200 tasks/s, identify the first saturated component instead of multiplying every server count. Partition by tenant or workflow, add backpressure and move long work to queues returning job IDs. At two tasks/s, simplify deployment while keeping the safety controls identical. Preserve ordering by account for conflicting writes. Parallelise independent authorised reads, while approvals and dependent writes follow state transitions.

Concurrency limits are a safety feature as well as a performance one. Cap per user, so nobody floods the system with parallel tasks; per tool, so a noisy downstream system is not overwhelmed; and globally. Encode value limits too, so many low-risk reads are allowed while the number and total value of refunds in flight stay bounded. A well-designed limit stops one prompt injection from becoming a cascade.

8. Prove the controls before widening autonomy

Two counts gate every expansion of autonomy: unsafe actions and duplicate effects, and the source requires both to be zero. High tool success alongside a rising duplicate-effect count is a deployment blocker, not a product win. A zero count is an operational gate, not proof of zero future risk, so record how much traffic and which attack tests stand behind it. Compare denials, overrides, approval delays and task completion with baselines too, so a nominally safe system does not quietly block every useful task.

  • indirect injection in emails, CRM records, tickets, database rows and fetched pages;
  • over-broad credentials that turn one manipulated plan into fleet-wide access;
  • unvalidated proposals, such as a confident $5,000 refund against a $500 limit;
  • lost responses that a naive retry turns into a second refund;
  • stale approvals or action loops that authorise the wrong state or retry into a large bill;
  • cross-tenant requests.

The go/no-go for autonomy has three parts: the obvious attack paths were exercised, the policy layer rejected them, and the agent fell back to read-only or human review instead of improvising around the control plane. A passing demo is not evidence that these paths are safe.

Integrating hundreds of applications without loading every tool

This is where the "enterprise assistant over 100+ applications" case joins this one. REST, function calling, Model Context Protocol (MCP) and agent frameworks are layers of one system, not competing technologies, and interviewers check whether you treat them that way.

REST is ideal when the interface is stable, the operations are deterministic and no reasoning is needed. A fixed workflow can call it directly. But a model does not natively understand authentication, endpoint discovery or request schemas, so REST alone never adds up to an assistant.

Function calling lets the model select a declared operation from natural language. The axis that separates it from REST is who decides to make the call: fixed application code, or the model. The wire call can be identical. The cost is not: another REST endpoint is cheap, while another function the model must choose between costs prompt space and selection accuracy. The source uses about twenty functions as a comfortable example and 1,500 functions across 100 applications as a catalog that strains selection and prompt size. These are scenario assumptions, not model-independent limits. Measure tool-selection accuracy, schema-token cost and latency on the actual catalog; maintain discovery metadata as schemas change.

MCP solves discoverability. One server per application advertises its tools and resources, so the assistant asks what is exposed instead of hardcoding schemas. MCP does not replace REST. The captured source describes MCP as JSON-RPC over standard input/output (stdio) or Streamable HTTP, and an MCP server may call REST, SOAP (Simple Object Access Protocol), SQL or a legacy system underneath. A tool protocol standardises access and discovery; it does not grant business permission.

An agent framework earns its place when a request needs multi-step reasoning. "Prepare a renewal report for our top customers and email their managers" means finding customers, retrieving CRM data, generating a report, storing a PDF and sending an email, and no single function coordinates that. A single agent suits one tool, a short workflow and deterministic execution. A multi-agent shape suits planning across many domains with independent specialists. Wrapping "Create a Jira ticket" in an orchestrator would be pure overhead.

Each integration layer has a different job.

Technology Best use
REST API Direct application communication
Function calling Small, deterministic tool execution
MCP Enterprise tool discovery and standardised AI integration
Agent framework Multi-step planning, orchestration, reasoning

Read the stack from the bottom. Execution never moves out of the REST, SOAP or SQL layer; each layer above adds a decision, not a new way to write. That is why the gateway and policy controls from the walkthrough still sit in front of the bottom layer however the call was chosen.

The tool registry is what makes this scale. Loading every MCP server up front does not. The registry sits between the planner and the universe of servers and loads only those relevant to the current task, which keeps the prompt small. In this design it also carries each tool's argument schema, data class and risk label, so the policy point can decide without asking the model. Treat the 1,500-function figure as the source's scenario, not a universal breaking point.

At 500-plus applications and 200,000 employees, the rest of the scaling list is short:

  • cache employee profiles, the org hierarchy and the holiday calendar, within freshness and privacy rules;
  • scale the planner, gateway and LLM routing as stateless horizontal services;
  • set per-user and per-application quotas, with circuit breakers against runaway agents;
  • run long workflows asynchronously and return a job ID;
  • use regional gateways, region-local MCP servers and data-residency controls.

No application trusts the LLM; applications trust enterprise identity. Every request carries the user's identity, an OAuth token, role-based or attribute-based access control (RBAC or ABAC) context and an audit record. The gateway establishes the actor and tenant for the target resource, so the backend does not trust the model directly. For HTTP MCP, validate token audience and use credentials issued for the receiving server. Do not forward an arbitrary incoming bearer token to every downstream application; exchange it or use the approved delegated credential for each target. This identity propagation is the same rule as the credential broker: the model receives context to reason with, never a secret to act with. Task state and audit stay separate from cross-session business truth.

The reported Salesforce prompt asks for the loop, tool interfaces, memory, orchestration and safety in one architecture, and this design answers each part. The loop is propose, validate, decide, execute, record, repeat, with a step budget. Tool interfaces are the registry's typed schemas with data class and risk. Memory is the task state store for workflow progress plus the ledger for what happened, and neither is business truth. Orchestration is the planner choosing one bounded action at a time over a queue partitioned by account. Safety is every layer below the planner.

Diagnose a slow or looping agent

The usual pivot after a good design is "the agent is slow and expensive". On this system the dominant driver is agent steps and tool calls, plus retries after failed or rejected actions. An agent that acts must be bounded before it is optimised, and the bounds already exist in the design: cap the steps, make the common paths deterministic, cache read-only tool results within the request, and let the approval gate stop the loop until a decision arrives. Do not answer by giving the loop a bigger model and a longer budget.

"The agent keeps calling tools repeatedly." It repeats a CRM lookup or retrieval until the request times out. "The tool-calling workflow times out." An external workflow exceeds the response deadline. Ask which tool is slow, whether it can run asynchronously and whether the result is needed immediately. The spoken line: "A tool timeout is not always an LLM issue. I would redesign slow side effects as async and keep the user informed."

Every strong cost answer follows four verbs in order. Measure, by tracing and attributing cost first. Route, matching the model and path to the risk. Bound, with limits on steps, tokens, timeouts and budgets. Cache safely, with tenant, permission and version in the cache key so one user's cached result never answers another user's request.

Deliver the answer in six moves: frame the business impact, decompose the path, name the largest measured driver, fix it safely, prove it with before-and-after numbers, and prevent recurrence. The proof metrics are steps per task, tool latency, retries, timeouts and cost per task.

When the interviewer wants unit economics, the ratio of model time to tool time decides the lever. When planning is expensive, batch safe reads into one planning pass. When tool calls dominate, cache safe reads and prefetch context. When human time is the cost, improve proposal clarity and risk classification, and tighten the threshold so only high-value cases reach a person. Never bypass a required approval to save time.

Investigate the refund near miss

The incident on this design is a near miss, and the trap is to say there was no problem because the gateway blocked it. Work through it as detect, contain, root cause and prevent.

A retail support assistant may summarise orders, draft replies, check policy and recommend refunds. It may not execute a refund above €250 without manager approval; for those it may only create a proposed refund ticket. On 8 July 2026 a support agent asked it to "handle all delayed VIP shipments from yesterday". The planner selected the refund_customer tool for eighteen orders, several of them above the threshold, including a €740 refund with no approval. The gateway blocked the high-value calls. Detect. Read the telemetry line by line. The planner line shows eighteen planned calls to refund_customer under policy refund_policy_v3 and planner model agent_planner_2026_07. The gateway line shows a €740 refund against a €250 no-approval limit, approval state missing, and a deny decision. The safety evaluator line shows six blocked calls, twelve allowed, a safer alternative of create_refund_review_ticket and a planner policy-compliance score of 0.42. Those lines tell two different stories. The gateway's critical line is enforcement working. The evaluator's line is the planner failing.

The source states that no unauthorised money moved. The twelve allowed calls passed the gateway, so they may have executed, and "no unauthorised money moved" is not the same as "no money moved". The trace alone cannot say whether those twelve refunds were legitimate, which is why containment includes auditing them.

Contain immediately: disable bulk refund planning, force all VIP refund actions into review-ticket mode, and add a user confirmation step for financial actions. Then audit the twelve allowed calls to confirm that the smaller refunds were legitimate. Preserve the proposals, policy context, schema and gateway records.

Root cause. The planner prompt agent_planner_2026_07 was deployed to make the agent "more action-oriented". Its examples emphasised completing workflows end to end and omitted bulk-action approval boundaries. The planner over-generalised "handle delayed shipments" into direct refund execution: it retrieved the refund policy and still failed to apply the threshold while planning. The gateway policy was unchanged and blocked correctly. Separate planner failure from enforcement success. This is a near miss, not a completed unauthorised transaction, and it still counts as an incident because the distribution of proposals got worse.

Prevent with defence in depth rather than a prompt edit:

  • risk-aware tool schemas that encode the approval threshold;
  • pre-execution policy simulation, so a planner change is tested against policy before it ships;
  • planner training examples that cover thresholds and bulk actions;
  • a separate action-risk classifier before tool calls;
  • hard enforcement kept in the gateway regardless of planner confidence.

The same pattern applies to account deletion, data export and permission changes. A malicious user can phrase any of them as operational cleanup, which makes this a fraud and unauthorised-action risk, not only a quality bug.

The weak answer is "the tool was blocked, so there is no problem; I would tell the agent to be more careful". The source scorecard rewards four things: reading planned, blocked and allowed calls with role, amount and approval state; separating planner failure from gateway success; auditing the plan, policy context, schema and gateway logs rather than editing the prompt; and naming the fraud and unauthorised-action risk. A spoken version is in the practice answers.

Make trade-offs explicit

Interviewers probe exactly four pairs, and each has a resolved shape: give a little on one side to protect something specific on the other. Flexible interpretation helps turn messy email into useful intent. Deterministic execution limits how that interpretation changes records. Fine-grained scopes add integration work, so scope irreversible effects first and share authorisation wrappers. Human approval adds queue latency, which is acceptable when the alternative grants uncontrolled financial authority. A central gateway provides one enforceable write path, while direct integrations multiply validation and audit responsibilities.

The source's four resolved trade-offs.

Trade-off Resolution
Agent flexibility vs deterministic workflow Flexible interpretation, deterministic execution. The model drafts, the workflow validates; letting the model choose the final action raises variance, audit complexity and blast radius
Fine-grained scopes vs integration burden Optimise scopes around irreversible effects first, then simplify with shared auth patterns and reusable wrappers
Automatic execution vs approval latency Tiered automation: low risk auto-runs, medium risk queues for review, high risk needs explicit approval or a second check. Accept approval latency to protect against irreversible financial harm
Central tool gateway vs direct integrations The gateway is the default, because it is the one place for auth, policy, audit, idempotency and schema validation; direct integrations multiply the places a bad prompt can reach a write API

This checklist is an authored addition. Assess what you can explain without reopening the walkthrough.

0 of 7 reasoning checks covered.

Why is "the model refuses" not a security control?

Because the model sees information and does not inherit trust. Any content it reads can manipulate it. Enforcement lives in the policy point, the broker and the gateway, so an injected instruction fails there even if the model is fooled.

What makes a retry safe?

A canonical argument hash as the idempotency seed, a durable business-action identifier, and a gateway that returns the stored receipt for a repeated key instead of calling the tool again. The downstream system must honour that contract or support reconciliation. Without it, do not retry a write; a lost response stays pending until confirmed.

What does an approval bind to, and why?

A snapshot of tenant, record version, amount and expiry, recorded with reviewer, timestamp, rationale and the exact payload. If the record changes before execution, the snapshot no longer matches, the approval is invalid and it is re-requested.

Where does the policy boundary end?

At allow, deny or approve, with scopes and a reason. The execution boundary ends at a scoped, logged side effect in a downstream system of record, which returns a receipt.

Why does validation run before policy?

So malformed or over-limit arguments, such as a $5,000 refund on a $500 task, are rejected before any authorisation logic executes, whatever the model's confidence.

What happens to writes when the credential broker is down?

They fail closed. Only reads with a cached, non-sensitive path that policy explicitly allows may degrade. The work is queued, the operator notified and the evidence kept. Never fall back to a broad static secret.

At what scale does function calling break, and what replaces it?

The source illustrates the problem with 1,500 functions across 100 applications and about twenty as a comfortable smaller catalog. These counts are assumptions to test, not a universal breaking point. MCP provides discovery and a tool registry loads only the servers and tools a task needs, carrying schema, data class, risk and scopes. Treat the count as the source's scenario, not a universal threshold.

Which two counts gate every autonomy expansion?

Unsafe actions and duplicate effects, both zero. Record the traffic and tests behind the zero, because zero observations do not prove future absence.

What is the refund near miss's root cause, and what is its fix?

A planner prompt made "more action-oriented" whose examples omitted bulk-action approval boundaries. The fix is risk-aware schemas that encode the threshold, policy simulation before execution, a separate risk classifier, better planner examples, and enforcement kept in the gateway. Contain first by disabling bulk refund planning and auditing the twelve allowed calls.

What is the first production gate?

That the control plane demonstrably prevents unauthorised actions, duplicate execution and uncontrolled side effects, not that the agent can do everything.

Why not let each tool integrate directly instead of routing every write through one gateway?

One gateway centralises authorisation, policy, validation, audit and idempotency in a single write path. Direct integrations multiply the places a bad prompt can reach a write API, and each one has to reimplement those checks correctly.

When does the agent stop?

On risk, ambiguity, missing state, a stale approval, a policy or broker failure, or a budget ceiling on steps, retries or spend. It pauses, escalates to a human or fails closed; it never improvises around the missing control.

The interviewer challenges your riskiest assumption: what if the email itself is trying to steer the agent into a refund it should not make?

Answer calmly and specifically. The email is untrusted input used only for classification and extraction. The policy engine outside the model decides whether the request is eligible for any write path. The workflow requires a durable action record, plus approval for risky cases. Content that looks like injection or carries conflicting instructions fails closed, and the ledger keeps it as evidence.

The agent keeps calling the same CRM lookup until the request times out. What do you do?

Treat it as a control-loop bug. Ask which tool repeats, what observation triggers it and whether state is preserved. Inspect the trace for the missing state transition. Now: max steps, a cached result, a better schema and a deterministic route. Later: budget tests and trace-based loop detection. Prevent with unit tests for tool selection and loop prevention.

The tool-calling workflow times out because an external system is slow. What do you do?

It is not always an LLM issue. Find the critical-path dependency, set per-tool timeouts, parallelise read-only calls and return a limited partial answer or an async job with status. Redesign slow side effects as async and keep the user informed. Later, add dependency SLAs and circuit breakers; prevent recurrence with a workflow design review before new tools.

Circuit breakers, rate limits, degradation when the model is unavailable? Per-tool breakers, per-user and per-tool quotas, and degradation to read-only or human-review mode, never to a bigger static credential

Close with the source's ninety-second decision memo:

"We're building an agent that turns unstructured email into safe operational action, but we are not giving the model unchecked authority. The model handles interpretation and recommendation; deterministic services handle identity, authorisation, idempotency, approvals, audit, and execution. The key trade-off is flexibility versus control: we accept some workflow rigidity so that refunds and CRM writes are gated, logged, and reversible where possible. The first gate is not 'the agent can do everything'; it is that the control plane demonstrably prevents unauthorised actions, duplicate execution, and uncontrolled side effects."

Recall the proposal-to-receipt contract

One sentence: the model proposes; deterministic systems decide; the idempotent gateway executes once and records a receipt. Name the disagreement between operations, security and finance in the first two minutes, because it is the design problem.

Ask first: which actions are reversible, where the money boundary sits, whose identity the agent acts as, what needs approval, which systems are the record, what audit must keep, how to stop in-flight work and what the peak task and tool load is.

Authenticate, propose one step, resolve a registered tool, validate arguments and data class, evaluate policy, obtain approval if needed, mint a scoped capability, execute with an operation key, persist the receipt and decide whether to continue. Business systems own truth. Workflow state owns progress.

Keep observations untrusted, credentials narrow, proposals validated and dangerous dimensions bounded. Required records are task, tool definition, proposal, policy decision, approval and receipt. Recheck approval snapshot and expiry. Fail writes closed on missing policy, credentials or durable evidence. Reconcile lost responses instead of repeating them.

The source assumes 50,000 users, twenty peak tasks/s, ten actions/task and forty to sixty model calls/s in bursts. At tenfold growth, partition and apply backpressure. Tool and value limits constrain damage as well as load. Large catalogs need task-relevant schema discovery and enterprise identity at every backend.

Read-only comes first, then reversible CRM writes with proven rollback. Money remains reviewed in the pilot. Zero observed unsafe and duplicate effects gate each expansion. Watch denials, overrides, approval delay and business completion together. A kill switch withdraws new authority and pauses work but cannot undo completed effects.

For the near miss, eighteen refunds were planned, six blocked and twelve allowed, and the €740 request exceeded the €250 no-approval limit. Distinguish the planner's unsafe proposals from the gateway's successful denial, and audit the twelve allowed operations as well as the six blocked ones. For slow or looping work, trace, route known intents, bound steps and retries, cache safe reads with tenant, permission and version in the key, and move slow effects to asynchronous jobs. Never extend an unbounded loop to make it more capable.

Policy, broker, approval, gateway and ledger are the reusable control plane; each customer brings adapters and configuration. Final mental model: propose, validate, decide, approve if needed, scope the credential, execute once, record, then stop or repeat within budget.
